# Database migrations

Each service owns its own schema's migrations under `db-meta/patches/`.
The engine (`src/migrations/engine.ts` → `runMigrations`) runs them **at
service startup, before any domain traffic is served** — a failed patch
leaves the service degraded, not silently stale.

Two artifacts travel with the patches:

- **`db-meta/MANIFEST.json`** — Ed25519-signed map of
  `patch_name → content_sha256`. The engine verifies the signature against
  `db-meta/keys.json` before trusting the hashes; an unsigned or badly
  signed manifest aborts the run (in `apply`/`check` mode).
- **`<schema>.primebrick_database_patches`** — per-service registry table
  (self-bootstrapped by the engine's DDL), the persisted provenance/order
  record: `patch_name`, `content_sha256`, `status`, `attempts`,
  `duration_ms`, `error`, `applied_by`, `resolved_by`, `atomic`.

## Patch semantics

- **Order** — filename-sorted (chronological `YYYYMMDDHHMMSS_<slug>.sql`).
  Every patch is **mandatory**: after one fails, later patches in that
  module do not execute.
- **Immutability** — a filename already registered with a different sha256
  is a security event, not a re-apply: never edit a shipped patch, ship a
  new one.
- **Pragmas** (header comments, first 40 lines):
  `-- pb:requires-review` parks the patch at `pending_review` until an
  admin approves it; `-- pb:no-transaction` opts a patch out of the
  default per-patch transaction (for `CREATE INDEX CONCURRENTLY` etc.).
- **Mode** is runtime config, not env: `<schema>.config_entries` key
  `db_migration.mode` = `apply` | `check` | `off`. Re-read after each run —
  a patch may change it. There is no "auto" guessing and nothing is
  generated from git hooks.
- **Advisory lock** — `pg_advisory_lock` keyed per schema serializes
  concurrent runners (multi-instance boot); `lockWaitMs` bounds the wait.
- **First-boot guard (anti-bifurcation)** — before any DDL the engine checks
  whether `<schema>.primebrick_database_patches` exists AND is populated. An
  absent or empty registry means "no service ever materialized this schema":
  the engine **refuses to run** unless `firstBoot: true` is passed
  (`primebrick-db apply --first-boot`, or the `dbPatches`/`MigrationEngine`
  option at boot). This closes the silent-bifurcation disaster — a service
  booting with a wrong schema name would otherwise migrate a pristine schema
  into a second phantom installation while the real data sits orphaned. A
  genuine first install opts in explicitly; everything else fails closed.
- **Seeds write the audit trail** — every seed `INSERT` must be followed
  by the matching `<table>_audit` rows. SQL seeds bypass the DAL, so
  `@AuditTrail` never fires for them; without the explicit block the
  version-history surface renders EMPTY for every seeded row. Convention
  (`config_entries` precedent): `action='INSERT'`,
  `changed_at`=row `created_at`, `changed_by='initial-setup'`,
  `version`=row `version`, `delta` = every column as
  `{old:null, new:value}` (`to_jsonb(t)` + `jsonb_each` covers all
  columns without enumerating them), idempotent via
  `WHERE NOT EXISTS` on the audit table.
  **Enforced at two levels**: the migration engine fails any pending
  patch that seeds a table whose `<t>_audit` twin exists in the catalog
  without carrying the audit rows (pre-SQL check — nothing executes),
  and check-standards' `seed-audit-trail` rule flags the same at lint
  time (auditable tables come from `snapshot-entities.json`). Escape
  hatch for legitimately non-audited seeds: `-- pb:no-audit-trail`.
  `seed_audit_exempt` grandfathers shipped pre-rule patches.

`runMigrations` returns `{ mode, nextMode?, degraded, applied[], failed[],
pendingReview[], skipped[], securityEvents[] }` — the service maps
`degraded`/`failed`/`pendingReview` onto its lifecycle state so the FE can
surface migration health.

## Admin remediation (the `db_patch` surface)

`src/migrations/status.ts` backs the admin page actions — plain registry
transitions the next run picks up:

| Helper | Transition |
|---|---|
| `retryFailedPatches` | `failed → pending` (next run retries, in order) |
| `approvePendingReview` | `pending_review → approved` (one named patch) |
| `resolveManually` | `failed`/`pending`/`pending_review → resolved_manual` |
| `registryStatus` | read all rows — the FE `db_patch` list |

## Schema diff — what `compare` sees

`compareSnapshots` diffs entity declarations against the catalog across:

- **tables / columns** — presence, rename heuristics;
- **type** (`typeMismatches`) and **nullability** (`nullabilityMismatches`);
- **indexes** (`onlyInEntityIndexes`, `onlyInDatabaseIndexes`,
  `indexMismatches` — columns, uniqueness, method, predicate);
- **foreign keys** (`onlyInEntityForeignKeys`, `onlyInDatabaseForeignKeys`,
  `foreignKeyMismatches`);
- **column DEFAULTs** (`defaultMismatches`) — `pg_attrdef` introspection
  via `pg_get_expr`, canonicalized by `normalizeDefaultExpr` (casts,
  outer parens, whitespace stripped *outside* quoted literals —
  `1::bigint` ≡ entity `1`, `'x'::character varying` ≡ `'x'`). Identity
  artifacts (`nextval('…_seq'::regclass)`) are NOT authored defaults and
  never diff; `GENERATED ALWAYS AS` expressions aren't DEFAULTs either.
  Emission: `ALTER COLUMN … SET DEFAULT <authored>` / `DROP DEFAULT` —
  catalog-only, no rewrite. Snapshots written before the capture carry
  no `capturesDefaults` marker — treated as *unknown*, never *absent*,
  so stale snapshots can't false-flag every declared default.

## `primebrick-db` CLI

`bin/primebrick-db` (`src/cli/primebrick-db.ts`) wraps the engine and the
schema-diff side for local/CI use:

```bash
primebrick-db compare --registry <module.ts> --url <pg-url> --schema <list> [--out db-meta]
    # entity snapshot vs catalog → snapshots JSON + unsigned .sql patch +
    # refreshed (UNSIGNED) MANIFEST.json entries
primebrick-db apply   --schema <s> --url <pg-url> --patches <dir> [--first-boot]
    # run the engine once — same code path as service boot; --first-boot
    # bypasses the absent/empty-registry guard for a genuine first install
primebrick-db check   --registry <module.ts> (--url <pg-url> | --snapshot <file>) --schema <list>
    # drift gate — exit 1 when entity intent is not fully applied
primebrick-db status  --schema <s> --url <pg-url>
    # print the <schema>.primebrick_database_patches registry
primebrick-db sign    --db-meta <dir> --key <b64|@file> --key-id <id>
    # re-sign MANIFEST.json after adding a patch (dev key locally,
    # release key only in CI)
primebrick-db keygen  --key-id <id> --trust <release|dev> [--out db-meta]
    # Ed25519 keypair; pubkey → keys.json, private key printed ONCE
```

`--schema` on `check`/`compare` is the **comma-separated schema domain**
(first = primary) — REQUIRED, with no env fallback: schema identity lives
in the service's `OWNED_SCHEMAS` const and the per-service wrapper scripts
(`db:check`, `db:meta:compare`) pass it through. Without the domain the CLI
could not resolve un-pinned builtin entities (they mount on the primary),
so it fails closed instead of silently assuming `public`.

Consumers wire it through their own scripts (`pnpm db:migrate`,
`db:check`, …) so the CLI itself never hardcodes connection settings.

**Signature trust:** `keys.json` entries carry `"release" | "dev"`;
`allowedTrust` on the engine defaults to `["release"]` — dev-signed
manifests run locally only when the service explicitly allows `dev`
(typically gated by NODE_ENV/dev mode).

## Fire-and-forget SQL — retired

`db-meta/fire-and-forget/` is **deprecated and deleted**. One-off
operational SQL (seeds, backfills, manual fix-ups) now lives in the
workspace `temp/` directory and is applied manually — **never committed**.
The only SQL that ships with a service is `db-meta/patches/` +
signed manifest.
